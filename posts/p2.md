Last week I settled on the general idea — a community hub for craft hobbyists, built around project logging rather than just photo sharing. This week I want to get more specific about what that actually means in terms of features and data.

**Who is this for?**

People who do slow, tactile hobbies — jigsaw puzzles, hama beads, embroidery, cross stitch, crochet, that kind of thing. What these communities have in common is that projects take time, sometimes weeks, and the satisfaction comes from the process as much as the finished result. A lot of existing platforms (Reddit, Instagram) only really support the finished product. I want to build something that values the in-between.

**Core functional requirements:**

Essential — without these the concept doesn't work:
- Users can create a project: name, craft type (from a set of categories), difficulty level, and status (not started / in progress / completed)
- Users can add progress updates to an existing project — a short note and a date
- The community can browse a feed of recently updated projects

Nice to have — if I have time:
- Filter projects by craft type or status
- A simple stats view: how many projects completed, favourite craft type

**What I'm not building:**

Image uploads. I know craft communities are very visual, but adding file upload functionality adds significant complexity to the tech stack and isn't core to the concept I'm exploring. The value here is in the structured data — being able to track progress over time — not in the photos. If I were pitching this as a real product I'd include it, but for this prototype I think it's the right thing to cut.

**Data model so far:**

Two main tables: `projects` (project_id, user_id, name, craft_type, difficulty, status, created_at) and `progress_notes` (note_id, project_id, content, date). The relationship between them is one project to many notes — clean and manageable in SQLite.

The brief talks about using the full-stack to create something technically meaningful. I think a two-table structure with a proper one-to-many relationship demonstrates that more clearly than a single flat table would.

Next I want to think about how users actually navigate between their own projects and the community feed — that's where the interaction design starts to matter.
